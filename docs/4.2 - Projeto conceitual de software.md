# Projeto Conceitual de Software: Driver Drowsiness & Distraction Detection System (DMS)

## 1. Visão Geral da Arquitetura de Software
A arquitetura do sistema foi projetada para operar em ambiente Linux Embarcado (Raspberry Pi OS) utilizando a linguagem C/C++. Para garantir os requisitos de tempo real estrito (RNF01) e processamento contínuo de 30 FPS (RNF02), o software abandona a execução sequencial típica de scripts em Python e adota o padrão **Produtor-Consumidor**.

O sistema é construído sobre **POSIX Threads (pthreads)**, dividindo as responsabilidades do sistema em fluxos de execução independentes, isolando falhas de rede (RNF03) das rotinas críticas de segurança (alarme local).

## 2. Decisões Tecnológicas e Dependências
*   **Linguagem:** C/C++ (Padrão C++17 recomendado para suporte a recursos modernos de concorrência e tipagem).
*   **Framework de Visão:** OpenCV (para manipulação de matrizes de imagem e conversão de cores).
*   **Detecção Facial e Marcos:** Biblioteca Dlib (C++) ou módulo nativo `cv::dnn` rodando um modelo leve (TFLite/ONNX) estritamente para extração de *Facial Landmarks* (6 pontos por olho). *Nota: O uso de frameworks pesados como PyTorch foi descartado para garantir o cumprimento da restrição de RAM < 100 MB (RNF04).*
*   **Captura de Vídeo:** API Video4Linux2 (V4L2) com interface UVC.
*   **Controle de Hardware:** Biblioteca `libgpiod` para manipulação determinística de I/O no *user-space* do Linux.

## 3. Pipeline de Processamento Visão/Sinal
A preocupação fundamental do pipeline é extrair a métrica geométrica sem sobrecarregar a CPU.

1.  **Aquisição (640x480 @ 30FPS):** A resolução foi matematicamente definida. Reduzir para 320x240 resultaria em perda crítica de densidade de pixels na região ocular (os olhos ocupariam menos de 15 pixels de largura, inviabilizando a localização dos marcos faciais). A resolução 640x480 garante ~30 pixels de largura por olho a 60cm de distância da câmera, ideal para o cálculo do EAR.
2.  **Pré-processamento:** Conversão imediata do frame de RGB (3 canais) para *Grayscale* (1 canal), reduzindo a quantidade de dados na memória em 66% antes do processamento geométrico.
3.  **Cálculo (EAR):** O algoritmo localiza a face, mapeia os marcos faciais e aplica a equação da Razão de Abertura Ocular (*Eye Aspect Ratio* - Soukupová & Čech).
4.  **Máquina de Estados de Fadiga:** O sistema mantém um contador de frames em que `EAR < 0.2`. Se atingir o limiar de 15 frames (aprox. 500ms), o sinal de disparo é enviado à thread de atuação.

## 4. Estrutura de Threads e Concorrência
O sistema será orquestrado por 4 threads principais sincronizadas através de **Mutexes** e **Variáveis de Condição (*Condition Variables*)**. A troca de imagens entre threads será feita por um *Buffer Circular* de tamanho fixo em memória RAM.

### T1: `capture_thread` (Produtor)
*   **Responsabilidade:** Conversar com os drivers V4L2 da câmera S600.
*   **Ação:** Captura o frame, converte para tons de cinza e o insere no Buffer Circular. Se o buffer encher, o frame mais antigo é sobrescrito (*Drop frame*, preferível a gerar gargalo na RAM).

### T2: `processing_thread` (Consumidor Crítico)
*   **Responsabilidade:** Processamento geométrico e decisão.
*   **Ação:** Aguarda (via `pthread_cond_wait`) a disponibilidade de um frame no buffer. Lê o frame protegido por mutex, executa o cálculo do EAR e da angulação da cabeça (Distração).
*   **Trigger:** Ao detectar anomalia (EAR baixo contínuo), altera o status de uma variável de controle atômica (`std::atomic<bool> alarm_state`).

### T3: `gpio_thread` (Atuador Local)
*   **Responsabilidade:** Salvar a vida do motorista de forma determinística (Latência < 100ms).
*   **Ação:** Monitora o `alarm_state`. Ao ser acionada, energiza imediatamente o pino GPIO conectado à base do transistor, acionando o buzzer ativo. Monitora o EAR para desligar o alarme quando o motorista acordar (RF07). Esta thread tem prioridade de execução alta no SO (escalonamento *Real-Time* se necessário).

### T4: `server_comm_thread` (Consumidor Assíncrono)
*   **Responsabilidade:** Telemetria via rede.
*   **Ação:** Lê o log interno de eventos críticos e tenta conexão via Sockets TCP/IP. Caso o veículo esteja em uma área sem cobertura de rede (zona de sombra), esta thread acumula os logs localmente até reestabelecer a conexão. Devido ao isolamento das *pthreads*, um *timeout* do TCP não irá travar o alarme sonoro nem a captura de frames.

## 5. Inserção no Sistema Operacional (OS Integration)
Para atender ao requisito de Inicialização Autônoma (RNF06), a aplicação não exigirá interação humana (mouse, teclado ou tela).
*   O sistema operacional será o **Raspberry Pi OS Lite** (sem interface gráfica Desktop instalada) para dedicar todos os núcleos e a RAM para a aplicação C++.
*   O executável final (compilado via *Makefile*) será gerenciado pelo **Systemd**.
*   Será criado um arquivo `dms-monitor.service` em `/etc/systemd/system/`. Este serviço garante que o binário inicie na fase final do *boot* da Raspberry Pi e seja automaticamente reiniciado em caso de travamento do software (*segfault*).
